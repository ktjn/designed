# Color theme research

**Recommendation**. Build a role-based palette with separate light and dark ramps. Use cool slate and blue for Default, and violet accents over restrained plum-gray neutrals for Editorial. Keep surfaces quiet, reserve saturated color for actions and feedback, and give control boundaries and focus their own contrast targets. Prototype both brands on the same component board before selecting final values.

## Current theme model

- Designed resolves DTCG primitives and semantic aliases into CSS, JSON, and TypeScript. `brand`, `color-scheme`, `contrast`, and `density` are independent settings. The compiler places brand declarations in a layer after the contrast layer. [Token package](../packages/tokens/README.md) · [Compiler](../packages/tokens/scripts/build-tokens.ts)
- Default uses blue actions. Editorial overrides primary action, focus, and selected fill with violet, with a dark override for selected fill. The current dark scheme shares Default's light primary action colors and maps selected and muted fill to the same neutral. Editorial focus takes precedence over the `more` focus token when their selectors match the same scope. [Base roles](../packages/tokens/src/semantic/base.json) · [Dark roles](../packages/tokens/src/semantic/dark.json) · [Editorial roles](../packages/tokens/src/semantic/brand-editorial.json) · [Dark Editorial roles](../packages/tokens/src/semantic/brand-editorial-dark.json) · [Compiler](../packages/tokens/scripts/build-tokens.ts)
- Primary action colors drive both filled buttons and link text. The primary fill also drives the active tab indicator. Danger action fill drives the filled danger button, form error text, and invalid field outlines. Those uses require different foreground or adjacent-color checks. [Button](../packages/react/src/button/button.module.css) · [Link](../packages/react/src/link/link.module.css) · [Tabs](../packages/react/src/tabs/tabs.module.css) · [Field](../packages/react/src/field/field.module.css) · [Input](../packages/react/src/input/input.module.css)
- Existing build tests check a limited set of text pairs by combining extracted CSS rules. Browser-computed values exercise the cascade, including nested scopes and media preferences. [Token tests](../packages/tokens/tests/build.test.ts) · [Nested scopes story](../apps/storybook/stories/theme.stories.tsx)

## Contrast and state requirements

| Concern                              | Standard or design target                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Text                                 | WCAG 2.2 AA requires at least 4.5:1 for normal text and 3:1 for large text. Apply the normal-text threshold to labels, links, placeholders, help, and status copy wherever they render, including on fills in interaction states. Use unrounded ratios for threshold checks. [WCAG 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)                                                                                                                                                                                                                                            |
| Meaningful boundaries and indicators | WCAG 2.2 AA requires at least 3:1 against adjacent colors for visual information needed to identify controls or their states and for meaningful parts of graphics. Decorative dividers and incidental background steps can stay subtle. Inactive controls have an exception. [WCAG 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)                                                                                                                                                                                                                                          |
| Keyboard focus                       | WCAG 2.2 AA requires visible focus and that author-created content leaves the focused component at least partly visible. For `more`, use the AAA focus appearance criterion as a design target. It specifies an indicator area equivalent to at least a 2 CSS pixel perimeter and 3:1 change in the same pixels from unfocused to focused. [WCAG 2.4.7](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html) · [WCAG 2.4.11](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html) · [WCAG 2.4.13](https://www.w3.org/WAI/WCAG22/Understanding/focus-appearance.html) |
| Status, selection, and links         | Pair color with a visible cue such as status copy or a distinguishable icon, a checkmark or underline for selection, and an underline for inline links. [WCAG 1.4.1](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)                                                                                                                                                                                                                                                                                                                                                                     |
| More contrast                        | Target 7:1 for normal text and 4.5:1 for large text in `more`, using WCAG's enhanced contrast criterion as the text benchmark. Strengthen meaningful borders and selected indicators in both brands. Test forced colors independently because the browser can substitute a user-selected palette. [WCAG 1.4.6](https://www.w3.org/WAI/WCAG22/Understanding/contrast-enhanced.html) · [Media Queries Level 5](https://www.w3.org/TR/mediaqueries-5/#prefers-contrast)                                                                                                                                    |

## Palette approaches

| Approach                                                             | Fit for Designed                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Patch existing aliases                                               | Smallest change for individual failing pairs. Keeps the current fixed ramps and the shared constraints wherever the same swatch serves text, fills, and indicators.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Map Radix Colors into existing semantic roles                        | Offers ready-made light and dark ramps with steps designed for surfaces, states, borders, fills, and text. The steps are starting points for Designed's actual adjacencies, and saturated fills need an explicit foreground. [Radix scale guide](https://www.radix-ui.com/colors/docs/palette-composition/understanding-the-scale) · [Radix palette composition](https://www.radix-ui.com/colors/docs/palette-composition/composing-a-palette)                                                                                                                                                                                                                                                                                                  |
| Author Designed ramps with Radix-style steps and Carbon-style layers | Makes the two brands and dark surfaces intentional while keeping the current token architecture. Carbon uses a common semantic vocabulary and progressively lighter neutral layers in dark mode. OKLCH supplies independent authoring controls for perceptual lightness, chroma, and hue. Choose in-gamut sRGB swatches and evaluate the resulting color pairs with WCAG relative luminance. [Carbon color anatomy](https://www.carbondesignsystem.com/building-blocks/foundations/color/overview) · [CSS Color 4, Oklab and OkLCh](https://www.w3.org/TR/css-color-4/#ok-lab) · [CSS Color 4, gamut mapping](https://www.w3.org/TR/css-color-4/#gamut-mapping) · [WCAG contrast calculation](https://www.w3.org/TR/WCAG22/#dfn-contrast-ratio) |

## Proposed direction

| Role                | Default                                                                                                               | Editorial                                                                                                  |
| ------------------- | --------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Light surfaces      | White canvas, pale slate panels, a slightly deeper neutral for nested or interactive surfaces                         | Off-white canvas, pale plum-gray panels, a slightly deeper plum-gray for nested or interactive surfaces    |
| Dark surfaces       | Near-black slate canvas, lifted slate cards and popovers, and brighter control boundaries                             | Deep plum-gray canvas and gently lifted plum-gray panels with the same hierarchy                           |
| Primary action      | Rich blue in light, brighter blue in dark                                                                             | Rich violet in light, brighter violet in dark                                                              |
| Selection and links | Blue-tinted selected surface, blue indicator, and blue link text with separate light and dark values                  | Violet-tinted selected surface, violet indicator, and violet link text with separate light and dark values |
| Status              | Blue info, green success, amber warning, and red danger, with paired text, tint, and visual indicators in each scheme | Same status meanings and scheme-specific colors                                                            |

- Keep the public token names and theme settings. Use the current semantic roles where they already fit. Add dedicated semantic roles where one swatch currently serves incompatible jobs, starting with link text, invalid field text and stroke, and selection indicators. Pair every solid primary and danger fill with its own readable on-fill foreground across default, hover, and active.
- Apply `more` to the effective brand and scheme. Increase text and boundary contrast, strengthen focus and selection cues, and retain the blue or violet identity wherever it meets the target. Use an offset or two-color focus treatment where a single ring cannot cover the actual adjacent surfaces. W3C's two-color technique uses bands at least 2 CSS pixels thick with at least 9:1 contrast between them, drawn over one solid surrounding color. [W3C technique C40](https://w3c.github.io/wcag/techniques/css/C40)
- Author ramps in OKLCH, then export fixed sRGB values through the existing token build. Compare the actual emitted colors after conversion and measure rendered combinations when opacity or color mixing changes the adjacent color. [CSS Color 4, gamut mapping](https://www.w3.org/TR/css-color-4/#gamut-mapping) · [Compiler](../packages/tokens/scripts/build-tokens.ts)

## Prototype acceptance

1. Fix scope composition first. Verify that effective brand, scheme, and contrast settings determine the same computed color pairs whether applied together, inherited, or explicitly reset in a nested scope. Exercise system preferences and portaled overlays in the browser. [Storybook theme toolbar](../apps/storybook/.storybook/preview.tsx) · [Theme scope](../packages/react/src/theme/theme.tsx) · [Portal architecture](architecture-log.md)
2. Compare the same board in all eight brand, scheme, and contrast combinations. Use text and an inline link, filled and secondary buttons, a field with validation, tabs or selection controls, a status alert, and an open overlay. Inspect resting, hover, active, selected, and keyboard-focused states. Give selection a visible checkmark, underline, or comparable shape that remains distinct when hover changes the fill.
3. Check computed foreground and background pairs across supported surfaces and states, including adjacent colors for necessary borders, selected indicators, and focus. Confirm that the two brands are distinguishable on the same screen, surfaces are legible in dark mode, and controls remain recognizable in grayscale. Review the rendered board alongside contrast measurements before changing the token defaults.
